# **从真实问题开始**

树莓派、Jetson、RDK、工控机和 PC 都可以成为机器人的计算平台。它们负责模型、ROS、界面和业务逻辑；PyMotion 负责把经过审核的动作交给电机和舵机，并在上位机失联时保持本地保护。

因此是否需要 SBC，不应由控制板强制决定。学习阶段可以直接使用现有 PC，脱机产品可以再加入 SBC；两者通过清晰接口连接，比把供电和机械层叠做成强绑定更灵活。

# **角色对比**

要让“角色对比”能够进入课程和产品，必须先说明：算力主机与执行控制器在 OS、任务、接口和故障行为上的差异。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

状态接口应回答“设备现在是什么状态、信息是否新鲜、为什么不能执行”，而不只是返回 ok。运行状态、控制者、桥接链路、故障码、队列深度、RSSI 与执行器反馈需要被组织成稳定模型，应用才有能力做降级、提示和自动报告。

硬件抽象并不是忽略差异，而是把差异放进适配器与能力描述。应用先查询设备支持的通道、反馈和协议，再决定开放哪些功能，能够避免在不兼容硬件上发送无效动作。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **四种组合**

如果只看最终动作，“四种组合”似乎并不复杂；真正的工作是PC+Lite、树莓派+Lite、Jetson+Lite、工控机+Lite 的场景与成本。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

PC、工控机和 SBC 的共同优势是操作系统、文件系统、模型生态和网络能力，适合视觉、SLAM、大模型与界面。它们的调度、启动和升级行为却不是电机安全边界。让上位机提出目标、让控制器管理动作，可以在保持算法自由度的同时缩小故障影响范围。

测试证据应覆盖正常路径、边界参数和故障路径。正常路径证明功能可用，边界参数证明校验有效，故障路径证明系统能停止和恢复；三者缺一，能力表都只能标为开发预览。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

# **连接方式**

围绕“连接方式”，首先要把问题拆到可验证层面：USB、UART、Wi-Fi 或其他已验证接口，不承诺未开发驱动。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

有线与无线连接应共享同一上层 API，却拥有不同可靠性定位。当前 V1 的正式生产控制通道是 ESP32-S3 原生 USB；Wi-Fi HTTP 属于受信局域网开发预览。无线适合配置、观察和实验，但本地超时与停止逻辑必须在断网后继续工作。

市场材料中的每个能力名称都应链接到可验证证据：公开 API、接线文档、测试报告、兼容清单或演示视频。用户看到的不只是功能列表，而是一条能够继续学习和开发的路径。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **供电原则**

“供电原则”回答的是一项具体工程问题。上位机和电机需要独立预算，不要让 Lite 承担不适合的大电流 SBC 供电。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

机器人电源要按峰值而不是平均值预算。电机启动、堵转和舵机同时起步都会产生瞬时电流，可能让逻辑电源下陷并触发复位。控制板、上位机和大功率执行器应明确电源域、共地方式、保险与反接保护，成品套件使用带 BMS 的电池包。

机器人问题经常表现为软件异常，根因却来自供电、接地、线束或机械负载。调试流程应同步记录电气条件与软件状态，避免在代码层反复修补物理问题。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **是否需要 Dock**

从产品实现看，“是否需要 Dock”不能停留在功能名称上。层叠安装仅是机械和供电配件，不是核心产品，可直接用支架和线缆连接。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

机器人电源要按峰值而不是平均值预算。电机启动、堵转和舵机同时起步都会产生瞬时电流，可能让逻辑电源下陷并触发复位。控制板、上位机和大功率执行器应明确电源域、共地方式、保险与反接保护，成品套件使用带 BMS 的电池包。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **选择决策**

读者在“选择决策”中真正需要掌握的是方法，而不只是结论。是否脱机、算力、功耗、成本、空间和维护。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

通用开发板提供自由度，机器人平台提供完成度。比较时应把电机驱动、电源、线材、协议、调试、升级、安全、SDK、示例和课程全部计入总拥有成本。对熟悉底层的工程师，自由度可能更重要；对课程和项目，减少重复集成通常更有价值。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **结论**

前面的分析可以归并成一个清楚判断：PyMotion 保持上位计算平台开放。这个判断同时约束产品定义与实现方法。高层可以持续升级算法，底层必须保持接口、状态和失败行为稳定；只有两者都成立，系统才有长期演进空间。

对读者而言，最重要的不是记住一串接口名，而是形成一套判断顺序：先确认任务与风险，再选择架构和硬件，随后验证正常、边界与故障路径，最后才讨论性能与规模。这个顺序能让技术决策和采购决策使用同一组证据。

正式发布时，结论中的每个能力都应对应版本化文档或测试结果。无法提供证据的内容可以作为路线图说明，但不应与当前交付能力混写。

# **PyMotion 的产品判断**

PyMotion 保持上位平台开放：PC-first 用于低成本学习，SBC 用于脱机和部署，工控机用于更稳定的现场计算。

真正有价值的控制器，不只是把电平送到接口，而是把动作变成有身份、有边界、有状态、可停止、可复盘的任务。这种能力会直接减少调试时间，也让学校课程、开发者原型和 OEM 评估能够沿同一套接口逐步升级。

PyMotion 的市场表达坚持把“已经交付”“正在验证”和“长期路线”分开。硬件接口存在不代表软件已完成，协议预留不代表兼容型号已验证，模拟测试也不等于真实硬件在环证据。专业感来自可核验，而不是把所有能力都写成满分。

# **结语**

树莓派、Jetson、RDK 或 PC 是上位计算平台，PyMotion 是下位执行控制器；产品不必强制集成 SBC Dock。

当这套方法落实到设备发现、统一 API、控制权、本地保护和结构化数据后，开发者可以把更多精力放在算法与应用本身。这也是 PyMotion 希望提供的价值：让物理 AI 从一次性的连线演示，逐步变成能够学习、扩展和交付的机器人系统。
