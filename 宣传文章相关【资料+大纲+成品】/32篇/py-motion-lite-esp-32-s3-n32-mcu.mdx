# **从真实问题开始**

摄像头传来一帧较大的 JPEG、Wi-Fi 突然重传、日志刚好写入存储，这些任务都有突发负载；与此同时，电机控制和通信超时仍应按稳定节奏运行。把它们全部压在一个 MCU 上，调试会越来越依赖运气。

PyMotion Lite 采用 ESP32-S3 与 N32 双 MCU，是一次职责隔离：ESP32 面向 PC、USB、网络和数据，N32 面向执行器、采样和本地保护。架构价值不在于多一颗芯片，而在于故障影响范围更可控。

# **单 MCU 的矛盾**

要让“单 MCU 的矛盾”能够进入课程和产品，必须先说明：Wi-Fi、摄像头、日志与周期控制竞争 CPU、内存、外设和故障域。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

有线与无线连接应共享同一上层 API，却拥有不同可靠性定位。当前 V1 的正式生产控制通道是 ESP32-S3 原生 USB；Wi-Fi HTTP 属于受信局域网开发预览。无线适合配置、观察和实验，但本地超时与停止逻辑必须在断网后继续工作。

一个可交付接口至少要回答五件事：谁发出的命令、参数是否在范围内、设备何时接受、执行状态如何返回、异常后怎样恢复。把这五项写清，应用代码才能从轮询与猜测中解放出来。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **ESP32-S3 职责**

如果只看最终动作，“ESP32-S3 职责”似乎并不复杂；真正的工作是USB/Wi-Fi、协议入口、数据转发、配置、设备管理，以实际固件为准。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

双 MCU 分工只有在通信合同清楚时才成立。帧头、长度、命令号、序号、CRC、状态码、超时、重发和版本兼容都要被定义；重复帧还要保证不会重复执行危险动作。ESP32 与 N32 的心跳应互相监督，使任一侧重启都能把执行器带回可预测状态。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

|  | **把功能写成合同**<br />对每个动作和状态统一描述输入范围、时间戳、有效期、超时、错误码与恢复方式，接口才能跨课程、套件和硬件版本复用。 |

# **N32 职责**

围绕“N32 职责”，首先要把问题拆到可验证层面：PWM、电机、舵机、编码器/ADC、超时停机，以原理图与固件为准。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

编码器把电机旋转转换为脉冲计数，里程计还需要减速比、每圈计数、轮径、轮距和采样周期。正反方向、溢出、丢脉冲与左右轮误差都要标定。里程计适合提供短时连续运动估计，但在打滑时仍会漂移，需要 IMU 与雷达纠正。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **MCU 间协议**

“MCU 间协议”回答的是一项具体工程问题。帧格式、CRC、序号、命令、状态、错误、心跳、重发和版本协商。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

控制租约类似带有效期的钥匙。客户端申请后获得 token，并周期续租；设备只接受当前持有者的运动命令。租约到期时，不是把权限交给下一条随机消息，而是先触发停止并清理旧状态。这样键盘、视觉和导航程序才能有明确切换规则。

系统恢复要比正常启动更严格：故障清除前旧命令不能自动复活，重新获得控制权后也应从安全状态开始。这个原则能阻止短暂重连把设备带回不可预期运动。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **故障场景**

从产品实现看，“故障场景”不能停留在功能名称上。ESP 重启、N32 无响应、CRC 错误、版本不兼容时的安全行为。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

状态接口应回答“设备现在是什么状态、信息是否新鲜、为什么不能执行”，而不只是返回 ok。运行状态、控制者、桥接链路、故障码、队列深度、RSSI 与执行器反馈需要被组织成稳定模型，应用才有能力做降级、提示和自动报告。

机器人问题经常表现为软件异常，根因却来自供电、接地、线束或机械负载。调试流程应同步记录电气条件与软件状态，避免在代码层反复修补物理问题。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **代价与取舍**

读者在“代价与取舍”中真正需要掌握的是方法，而不只是结论。BOM、固件复杂度、升级一致性和测试成本。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

通用开发板提供自由度，机器人平台提供完成度。比较时应把电机驱动、电源、线材、协议、调试、升级、安全、SDK、示例和课程全部计入总拥有成本。对熟悉底层的工程师，自由度可能更重要；对课程和项目，减少重复集成通常更有价值。

状态设计最好采用“值、有效标志、采样时间、来源、故障原因”的组合。这样同一个上位程序既能处理真实硬件，也能处理回放数据或仿真数据，而不会把缺失值误当成真实测量。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **结论**

前面的分析可以归并成一个清楚判断：双 MCU 的价值来自职责和协议，不只是多一颗芯片。这个判断同时约束产品定义与实现方法。高层可以持续升级算法，底层必须保持接口、状态和失败行为稳定；只有两者都成立，系统才有长期演进空间。

对读者而言，最重要的不是记住一串接口名，而是形成一套判断顺序：先确认任务与风险，再选择架构和硬件，随后验证正常、边界与故障路径，最后才讨论性能与规模。这个顺序能让技术决策和采购决策使用同一组证据。

正式发布时，结论中的每个能力都应对应版本化文档或测试结果。无法提供证据的内容可以作为路线图说明，但不应与当前交付能力混写。

# **PyMotion 的产品判断**

ESP32-S3 处理原生 USB、联网、RPC、状态和数据；N32 管理执行器与本地超时。两者通过版本化帧协议交换命令和状态。

真正有价值的控制器，不只是把电平送到接口，而是把动作变成有身份、有边界、有状态、可停止、可复盘的任务。这种能力会直接减少调试时间，也让学校课程、开发者原型和 OEM 评估能够沿同一套接口逐步升级。

双 MCU 将联网与数据任务同电机实时执行隔离，使系统职责清晰并便于故障收敛。

当这套方法落实到设备发现、统一 API、控制权、本地保护和结构化数据后，开发者可以把更多精力放在算法与应用本身。这也是 PyMotion 希望提供的价值：让物理 AI 从一次性的连线演示，逐步变成能够学习、扩展和交付的机器人系统。
