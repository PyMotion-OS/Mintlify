# **从真实问题开始**

一台视觉小车最吸引人的不是摄像头画面，而是画面中的目标真的改变了轮子的动作：目标在左边，小车转向；目标变远，小车靠近；目标消失，小车停止搜索。

PyMotion Vision Car 把 PC 端识别与板端执行拆开，让学生能看见视觉误差如何变成结构化动作，也能观察超声波、碰撞开关和通信状态如何覆盖视觉指令。

# **产品定位**

如果只看最终动作，“产品定位”似乎并不复杂；真正的工作是说明它是 PC 端 AI 视觉机器人，不宣传 SLAM 和高速视频。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

SLAM 需要明确 base、odom、map 与传感器坐标系，并让编码器、IMU 和雷达数据拥有可对齐时间戳。地图是否好看只是结果之一，还应评估回环、一致性、轨迹漂移、数据丢包和重定位。课程越能展示误差来源，学生学到的就越接近真实工程。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **硬件组成**

围绕“硬件组成”，首先要把问题拆到可验证层面：Lite、底盘、电机、摄像头、ToF/超声波、巡线、IMU、碰撞、供电。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

HC-SR04 的 Echo 常为 5 V 电平，接入 3.3 V MCU 前需要分压或电平转换；测量还要区分有效距离、无回波和数据过期。ToF 模块通常更紧凑、近距离表现更稳定，但同样需要核对接口电压、视场角和环境光条件。

市场材料中的每个能力名称都应链接到可验证证据：公开 API、接线文档、测试报告、兼容清单或演示视频。用户看到的不只是功能列表，而是一条能够继续学习和开发的路径。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **系统架构**

“系统架构”回答的是一项具体工程问题。视频到 PC，识别结果变成结构化动作，Lite 执行并反馈。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

结构化运动数据至少应包含 timestamp、device_id、task_id、transport、命令、反馈、运行状态和故障原因。CSV 适合快速画曲线，JSONL 适合保留嵌套状态，summary.json 适合验收汇总。三者共享同一任务 ID 后，现场问题才能从结果追溯到过程。

状态设计最好采用“值、有效标志、采样时间、来源、故障原因”的组合。这样同一个上位程序既能处理真实硬件，也能处理回放数据或仿真数据，而不会把缺失值误当成真实测量。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **基础体验**

从产品实现看，“基础体验”不能停留在功能名称上。键盘/手柄、视频预览、传感器查看和安全停止。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

感知数据必须同时携带数值、采样时间和有效状态。一个距离值如果没有时间戳，就无法判断它属于当前画面还是上一秒；一个无回波如果被编码成零厘米，上层会把传感器故障误判成贴近障碍。可靠接口首先统一语义，然后才讨论滤波和算法。

硬件抽象并不是忽略差异，而是把差异放进适配器与能力描述。应用先查询设备支持的通道、反馈和协议，再决定开放哪些功能，能够避免在不兼容硬件上发送无效动作。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **视觉能力**

读者在“视觉能力”中真正需要掌握的是方法，而不只是结论。颜色、二维码、人脸或目标检测，明确算法运行位置和模型来源。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

系统工程的基本方法是先定义合同，再实现模块。合同描述输入范围、输出含义、状态有效期、资源限制和失败模式；模块可以替换，但合同应保持稳定。这样课程示例、整机应用与 OEM 固件才能共享同一条演进路径。

可观察性并不意味着把所有内部变量都暴露给用户。稳定产品应选择少量但含义明确的状态字段，再通过事件和诊断报告提供深度信息，使日常使用简单、工程排障充分。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

# **闭环案例**

要让“闭环案例”能够进入课程和产品，必须先说明：目标居中、距离控制、丢失停车、碰撞优先级和状态机。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

物理 AI 的关键不是设备外形，而是信息是否形成闭环：传感器描述环境，算法给出目标与计划，执行层把计划约束成动作，反馈再判断结果是否符合预期。只要缺少反馈或失败处理，系统就仍然是单向遥控，而不是能够持续修正的智能体。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **16 个实验路径**

如果只看最终动作，“16 个实验路径”似乎并不复杂；真正的工作是分成连接、运动、视觉、融合、安全五阶段，引用课程文档。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

有线与无线连接应共享同一上层 API，却拥有不同可靠性定位。当前 V1 的正式生产控制通道是 ESP32-S3 原生 USB；Wi-Fi HTTP 属于受信局域网开发预览。无线适合配置、观察和实验，但本地超时与停止逻辑必须在断网后继续工作。

测试证据应覆盖正常路径、边界参数和故障路径。正常路径证明功能可用，边界参数证明校验有效，故障路径证明系统能停止和恢复；三者缺一，能力表都只能标为开发预览。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **SKU 与边界**

围绕“SKU 与边界”，首先要把问题拆到可验证层面：Standard/Pro 差异、真实售价占位、USB 摄像头选项。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

OV2640 一类摄像头常在板端输出 JPEG，图像大小会随分辨率、质量和画面复杂度变化。传输策略应设置队列上限和过期丢帧，优先保证最新画面；同时把采集、编码、发送和电机 RPC 分开调度，避免图像阻塞控制路径。

一个可交付接口至少要回答五件事：谁发出的命令、参数是否在范围内、设备何时接受、执行状态如何返回、异常后怎样恢复。把这五项写清，应用代码才能从轮询与猜测中解放出来。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **结论**

前面的分析可以归并成一个清楚判断：强调从视觉结果到安全动作的完整闭环。这个判断同时约束产品定义与实现方法。高层可以持续升级算法，底层必须保持接口、状态和失败行为稳定；只有两者都成立，系统才有长期演进空间。

对读者而言，最重要的不是记住一串接口名，而是形成一套判断顺序：先确认任务与风险，再选择架构和硬件，随后验证正常、边界与故障路径，最后才讨论性能与规模。这个顺序能让技术决策和采购决策使用同一组证据。

正式发布时，结论中的每个能力都应对应版本化文档或测试结果。无法提供证据的内容可以作为路线图说明，但不应与当前交付能力混写。
