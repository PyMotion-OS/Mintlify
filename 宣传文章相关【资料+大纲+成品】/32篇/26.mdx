# **从真实问题开始**

“找到红色物体并靠近”不是把一句语音映射成前进命令。系统要先理解目标，再调用视觉、搜索、移动、测距和播报技能，并在任何阶段接受用户的停止指令。

大模型适合生成意图与有限计划，底层控制器负责可信执行。把 JSON Schema、技能白名单、异步任务、世界状态和安全停止串起来，物理 AI 才从语音玩具变成可以教学和审查的系统。

# **不是语音遥控**

从产品实现看，“不是语音遥控”不能停留在功能名称上。区分固定口令、LLM 意图、任务规划和物理闭环。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

大模型输出具有概率性，同一句话可能得到不同措辞，响应时间也会随上下文和网络变化。工程系统应让模型输出“意图、参数、确认要求和原因”，而不是底层寄存器值；模型失败时可以重试或询问，执行层失败时则必须保持输出受控。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **输入与输出**

读者在“输入与输出”中真正需要掌握的是方法，而不只是结论。麦克风、摄像头、距离、IMU、语音回答和运动执行。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

感知数据必须同时携带数值、采样时间和有效状态。一个距离值如果没有时间戳，就无法判断它属于当前画面还是上一秒；一个无回波如果被编码成零厘米，上层会把传感器故障误判成贴近障碍。可靠接口首先统一语义，然后才讨论滤波和算法。

一个可交付接口至少要回答五件事：谁发出的命令、参数是否在范围内、设备何时接受、执行状态如何返回、异常后怎样恢复。把这五项写清，应用代码才能从轮询与猜测中解放出来。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

# **结构化计划**

要让“结构化计划”能够进入课程和产品，必须先说明：JSON Schema、技能白名单、参数范围、确认标志和拒绝原因。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

JSON Schema 的价值不是让结果看起来整齐，而是把自由文本压缩成有限合同。技能名称来自白名单，速度、角度和距离有明确范围，未知字段被拒绝，危险动作需要确认。校验通过只代表“格式和范围合法”，真正执行还要检查控制权、设备状态与环境条件。

可观察性并不意味着把所有内部变量都暴露给用户。稳定产品应选择少量但含义明确的状态字段，再通过事件和诊断报告提供深度信息，使日常使用简单、工程排障充分。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **技能库**

如果只看最终动作，“技能库”似乎并不复杂；真正的工作是前进、停止、测距、拍照、找颜色等技能的接口和执行结果。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

机器人技能应像受控任务：拥有明确参数、开始条件、进度、取消入口、超时和结果。长任务不能阻塞语音监听；有限重规划只允许重试、搜索、停止或询问用户等经过审核的策略，避免模型在异常时自由创造底层动作。

测试证据应覆盖正常路径、边界参数和故障路径。正常路径证明功能可用，边界参数证明校验有效，故障路径证明系统能停止和恢复；三者缺一，能力表都只能标为开发预览。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **异步执行**

围绕“异步执行”，首先要把问题拆到可验证层面：进度、取消、超时、用户插入“停止”和播放/收音半双工。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

TTL 总线舵机常用电源、地和半双工数据三根线串接，每个舵机依靠 ID 寻址。部分型号可读取位置、电压、温度和运动状态，但字段与协议并不统一。当前 PyMotion 协议合同支持最多六个舵机的批量动作，具体型号与供电范围仍以兼容清单为准。

状态设计最好采用“值、有效标志、采样时间、来源、故障原因”的组合。这样同一个上位程序既能处理真实硬件，也能处理回放数据或仿真数据，而不会把缺失值误当成真实测量。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **视觉闭环**

“视觉闭环”回答的是一项具体工程问题。找目标、居中、接近、丢失停车和碰撞优先级。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

物理 AI 的关键不是设备外形，而是信息是否形成闭环：传感器描述环境，算法给出目标与计划，执行层把计划约束成动作，反馈再判断结果是否符合预期。只要缺少反馈或失败处理，系统就仍然是单向遥控，而不是能够持续修正的智能体。

机器人问题经常表现为软件异常，根因却来自供电、接地、线束或机械负载。调试流程应同步记录电气条件与软件状态，避免在代码层反复修补物理问题。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **重规划边界**

从产品实现看，“重规划边界”不能停留在功能名称上。仅允许重试、搜索、停止、询问等有限策略，不让模型自由生成底层程序。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **数据与安全**

读者在“数据与安全”中真正需要掌握的是方法，而不只是结论。保存语音、计划、视觉、动作和故障，断网/异常本地停止。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

状态接口应回答“设备现在是什么状态、信息是否新鲜、为什么不能执行”，而不只是返回 ok。运行状态、控制者、桥接链路、故障码、队列深度、RSSI 与执行器反馈需要被组织成稳定模型，应用才有能力做降级、提示和自动报告。

市场材料中的每个能力名称都应链接到可验证证据：公开 API、接线文档、测试报告、兼容清单或演示视频。用户看到的不只是功能列表，而是一条能够继续学习和开发的路径。

# **结论**

前面的分析可以归并成一个清楚判断：大模型负责决策接口，控制器负责可信执行。这个判断同时约束产品定义与实现方法。高层可以持续升级算法，底层必须保持接口、状态和失败行为稳定；只有两者都成立，系统才有长期演进空间。

对读者而言，最重要的不是记住一串接口名，而是形成一套判断顺序：先确认任务与风险，再选择架构和硬件，随后验证正常、边界与故障路径，最后才讨论性能与规模。这个顺序能让技术决策和采购决策使用同一组证据。

正式发布时，结论中的每个能力都应对应版本化文档或测试结果。无法提供证据的内容可以作为路线图说明，但不应与当前交付能力混写。

# **PyMotion 的产品判断**

物理 AI 套件让大模型只调用经过审核的 PyMotion 技能，执行进度、失败原因与世界状态再回到上层规划。
