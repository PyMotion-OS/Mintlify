# **从真实问题开始**

机器人不会因为 Python 程序崩溃而自动理解“应该停车”。如果最后一条前进命令一直有效，拔线、断 Wi-Fi、进程被强制结束都可能留下持续运动的执行器。

心跳、通信超时、看门狗和故障锁存共同把“程序可能随时消失”变成可处理的系统条件。可靠性不是一句宣传语，而是一组能反复注入故障、测量停止和生成报告的工程机制。

# **故障故事**

“故障故事”回答的是一项具体工程问题。Python 被强制结束但电机仍保持旧命令的风险。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

状态接口应回答“设备现在是什么状态、信息是否新鲜、为什么不能执行”，而不只是返回 ok。运行状态、控制者、桥接链路、故障码、队列深度、RSSI 与执行器反馈需要被组织成稳定模型，应用才有能力做降级、提示和自动报告。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **三层心跳**

从产品实现看，“三层心跳”不能停留在功能名称上。PC-ESP、ESP-N32、本地硬件看门狗分别监测什么。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

双 MCU 分工只有在通信合同清楚时才成立。帧头、长度、命令号、序号、CRC、状态码、超时、重发和版本兼容都要被定义；重复帧还要保证不会重复执行危险动作。ESP32 与 N32 的心跳应互相监督，使任一侧重启都能把执行器带回可预测状态。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **停止策略**

读者在“停止策略”中真正需要掌握的是方法，而不只是结论。超时阈值、立即停止/缓停、舵机安全位和输出关闭的区别。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

可靠停机通常由多层监督共同完成：PC 心跳判断应用是否还活着，ESP 检查控制租约和上位链路，N32 检查执行命令是否持续有效，驱动与电源处理短路和过流。故障锁存用于阻止旧命令自动恢复；控制停止则不能被宣传成经过认证的安全急停。

系统恢复要比正常启动更严格：故障清除前旧命令不能自动复活，重新获得控制权后也应从安全状态开始。这个原则能阻止短暂重连把设备带回不可预期运动。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **故障锁存**

要让“故障锁存”能够进入课程和产品，必须先说明：为什么故障后不应自动恢复旧动作，如何清除并重新申请控制权。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

控制租约类似带有效期的钥匙。客户端申请后获得 token，并周期续租；设备只接受当前持有者的运动命令。租约到期时，不是把权限交给下一条随机消息，而是先触发停止并清理旧状态。这样键盘、视觉和导航程序才能有明确切换规则。

测试证据应覆盖正常路径、边界参数和故障路径。正常路径证明功能可用，边界参数证明校验有效，故障路径证明系统能停止和恢复；三者缺一，能力表都只能标为开发预览。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **测试方法**

如果只看最终动作，“测试方法”似乎并不复杂；真正的工作是Ctrl+C、杀进程、断网、重启路由器、拔 USB、MCU 失联的逐项步骤。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

有线与无线连接应共享同一上层 API，却拥有不同可靠性定位。当前 V1 的正式生产控制通道是 ESP32-S3 原生 USB；Wi-Fi HTTP 属于受信局域网开发预览。无线适合配置、观察和实验，但本地超时与停止逻辑必须在断网后继续工作。

硬件抽象并不是忽略差异，而是把差异放进适配器与能力描述。应用先查询设备支持的通道、反馈和协议，再决定开放哪些功能，能够避免在不兼容硬件上发送无效动作。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

# **测试结果**

围绕“测试结果”，首先要把问题拆到可验证层面：预期、实测、是否通过、固件版本和异常说明。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

升级链路必须把固件版本、硬件版本、协议版本、镜像摘要和恢复路径绑定起来。当前 SDK 暴露 ESP32 的 HTTPS OTA 状态和启动接口；N32 在线升级只有在 IAP 与失败恢复完整验证后才能作为双 MCU OTA 对外发布。

可观察性并不意味着把所有内部变量都暴露给用户。稳定产品应选择少量但含义明确的状态字段，再通过事件和诊断报告提供深度信息，使日常使用简单、工程排障充分。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **边界**

“边界”回答的是一项具体工程问题。STOP 不等同安全急停，Lite 不具备功能安全认证。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

PLC 的优势来自标准化工程体系：工业电气、环境指标、供应链、维护习惯和认证共同构成可信度。轻量控制器可以承担教育、原型或非安全关键辅助动作，但不能替代安全 PLC、安全继电器和经过认证的运动控制系统。

市场材料中的每个能力名称都应链接到可验证证据：公开 API、接线文档、测试报告、兼容清单或演示视频。用户看到的不只是功能列表，而是一条能够继续学习和开发的路径。

# **PyMotion 的产品判断**

PyMotion 的 SDK 会维护控制心跳并在上下文退出时停止输出；真正的安全底线仍由 ESP32 与 N32 的独立超时监督承担。

真正有价值的控制器，不只是把电平送到接口，而是把动作变成有身份、有边界、有状态、可停止、可复盘的任务。这种能力会直接减少调试时间，也让学校课程、开发者原型和 OEM 评估能够沿同一套接口逐步升级。
