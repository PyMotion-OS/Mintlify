# **从真实问题开始**

开发者想研究接口，教师想组织课程，OEM 想评估嵌入产品，他们不应该被迫购买同一套模糊组合。SKU 越清楚，用户越容易知道盒子里有什么、还要自备什么、能够完成哪些实验。

PyMotion 产品线应按学习目标和执行器组织：Lite 是入口，视觉小车、SLAM 小车、六轴机械臂和物理 AI 套件分别完成不同闭环，教学包则补上教师资料、备件与验收。

# **快速判断**

“快速判断”回答的是一项具体工程问题。用五个问题判断：做什么、已有何种结构、是否要视觉/SLAM/机械臂、人数、是否 OEM。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

SLAM 需要明确 base、odom、map 与传感器坐标系，并让编码器、IMU 和雷达数据拥有可对齐时间戳。地图是否好看只是结果之一，还应评估回环、一致性、轨迹漂移、数据丢包和重定位。课程越能展示误差来源，学生学到的就越接近真实工程。

状态设计最好采用“值、有效标志、采样时间、来源、故障原因”的组合。这样同一个上位程序既能处理真实硬件，也能处理回放数据或仿真数据，而不会把缺失值误当成真实测量。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **Lite Core/Starter**

从产品实现看，“Lite Core/Starter”不能停留在功能名称上。适合底层接口和基础实验，列清包含/不包含内容。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

系统工程的基本方法是先定义合同，再实现模块。合同描述输入范围、输出含义、状态有效期、资源限制和失败模式；模块可以替换，但合同应保持稳定。这样课程示例、整机应用与 OEM 固件才能共享同一条演进路径。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **Vision Car**

读者在“Vision Car”中真正需要掌握的是方法，而不只是结论。Standard/Pro 的差异、16 实验、适合课程和开发者。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

系统工程的基本方法是先定义合同，再实现模块。合同描述输入范围、输出含义、状态有效期、资源限制和失败模式；模块可以替换，但合同应保持稳定。这样课程示例、整机应用与 OEM 固件才能共享同一条演进路径。

测试证据应覆盖正常路径、边界参数和故障路径。正常路径证明功能可用，边界参数证明校验有效，故障路径证明系统能停止和恢复；三者缺一，能力表都只能标为开发预览。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **SLAM Car**

要让“SLAM Car”能够进入课程和产品，必须先说明：编码器、IMU、雷达和高级课程，说明 PC/算法要求。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

编码器把电机旋转转换为脉冲计数，里程计还需要减速比、每圈计数、轮径、轮距和采样周期。正反方向、溢出、丢脉冲与左右轮误差都要标定。里程计适合提供短时连续运动估计，但在打滑时仍会漂移，需要 IMU 与雷达纠正。

系统恢复要比正常启动更严格：故障清除前旧命令不能自动复活，重新获得控制权后也应从安全状态开始。这个原则能阻止短暂重连把设备带回不可预期运动。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **六轴机械臂**

如果只看最终动作，“六轴机械臂”似乎并不复杂；真正的工作是总线舵机、供电、课程和负载边界。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

TTL 总线舵机常用电源、地和半双工数据三根线串接，每个舵机依靠 ID 寻址。部分型号可读取位置、电压、温度和运动状态，但字段与协议并不统一。当前 PyMotion 协议合同支持最多六个舵机的批量动作，具体型号与供电范围仍以兼容清单为准。

硬件抽象并不是忽略差异，而是把差异放进适配器与能力描述。应用先查询设备支持的通道、反馈和协议，再决定开放哪些功能，能够避免在不兼容硬件上发送无效动作。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

# **物理 AI 套件**

围绕“物理 AI 套件”，首先要把问题拆到可验证层面：麦克风、扬声器、视觉、LLM 和16实验，说明云服务成本/网络需求。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

物理 AI 的关键不是设备外形，而是信息是否形成闭环：传感器描述环境，算法给出目标与计划，执行层把计划约束成动作，反馈再判断结果是否符合预期。只要缺少反馈或失败处理，系统就仍然是单向遥控，而不是能够持续修正的智能体。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **结论**

前面的分析可以归并成一个清楚判断：推荐最小可完成目标的 SKU，并给升级路径。这个判断同时约束产品定义与实现方法。高层可以持续升级算法，底层必须保持接口、状态和失败行为稳定；只有两者都成立，系统才有长期演进空间。

对读者而言，最重要的不是记住一串接口名，而是形成一套判断顺序：先确认任务与风险，再选择架构和硬件，随后验证正常、边界与故障路径，最后才讨论性能与规模。这个顺序能让技术决策和采购决策使用同一组证据。

正式发布时，结论中的每个能力都应对应版本化文档或测试结果。无法提供证据的内容可以作为路线图说明，但不应与当前交付能力混写。
