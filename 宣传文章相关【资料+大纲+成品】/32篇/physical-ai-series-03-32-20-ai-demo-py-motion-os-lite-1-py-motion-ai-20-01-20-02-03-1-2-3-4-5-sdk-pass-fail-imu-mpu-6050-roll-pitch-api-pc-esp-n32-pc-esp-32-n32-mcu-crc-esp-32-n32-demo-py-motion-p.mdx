# **从真实问题开始**

用户说出“找到红色积木，靠近到二十厘米，然后回来告诉我”，听起来只有一句话。机器人真正执行时，却要连续完成听见、识别对象、规划搜索、选择速度、避开障碍、判断距离、停止和播报结果。

任何一个环节都可能失败，因此端到端系统不能只画一条理想箭头。它需要明确每一步的输入、输出、超时、失败原因和恢复策略，并把整个任务放进同一条时间线中。

# **用户任务**

读者在“用户任务”中真正需要掌握的是方法，而不只是结论。展开任务隐含条件：识别目标、定位、避障、距离判断、停止和结果反馈。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

感知数据必须同时携带数值、采样时间和有效状态。一个距离值如果没有时间戳，就无法判断它属于当前画面还是上一秒；一个无回波如果被编码成零厘米，上层会把传感器故障误判成贴近障碍。可靠接口首先统一语义，然后才讨论滤波和算法。

版本管理不仅是显示一个固件号，还要关联协议合同、硬件修订、配置格式和 SDK 兼容范围。发生问题时能够还原当时组合，比单纯追求频繁升级更重要。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **感知链路**

要让“感知链路”能够进入课程和产品，必须先说明：麦克风/文本、摄像头、距离传感器和 IMU 分别提供什么信息。随后再用可重复实验验证边界，才能把一次成功转化为稳定能力。

MPU6050 提供三轴加速度和三轴角速度，静止零偏与安装方向决定基础质量。互补滤波可以得到较稳定的 roll/pitch，但器件没有磁力计，无法仅靠自身提供长期可靠的绝对航向。课程应把漂移显示出来，而不是隐藏限制。

可观察性并不意味着把所有内部变量都暴露给用户。稳定产品应选择少量但含义明确的状态字段，再通过事件和诊断报告提供深度信息，使日常使用简单、工程排障充分。

工程文档还应标出供电、电平、速率、资源占用和兼容版本。清楚的边界不会削弱产品吸引力，反而会让专业用户相信后续扩展是可管理的。

# **理解与规划**

如果只看最终动作，“理解与规划”似乎并不复杂；真正的工作是意图提取、对象属性、任务步骤和确认机制。这要求系统同时保留控制流、数据流和故障流，而不是在异常发生后只打印一行错误。

大模型输出具有概率性，同一句话可能得到不同措辞，响应时间也会随上下文和网络变化。工程系统应让模型输出“意图、参数、确认要求和原因”，而不是底层寄存器值；模型失败时可以重试或询问，执行层失败时则必须保持输出受控。

市场材料中的每个能力名称都应链接到可验证证据：公开 API、接线文档、测试报告、兼容清单或演示视频。用户看到的不只是功能列表，而是一条能够继续学习和开发的路径。

最终输出不应只有终端打印，还要包含状态快照、事件记录和摘要报告。这样学生能理解系统，工程师也能快速复盘问题。

# **技能执行**

围绕“技能执行”，首先要把问题拆到可验证层面：寻找、转向、接近、停车、播报等技能的输入、输出、超时和失败原因。如果这里只展示一个成功视频，读者仍无法判断系统是否能在不同设备、不同负载和异常条件下复现。

可靠停机通常由多层监督共同完成：PC 心跳判断应用是否还活着，ESP 检查控制租约和上位链路，N32 检查执行命令是否持续有效，驱动与电源处理短路和过流。故障锁存用于阻止旧命令自动恢复；控制停止则不能被宣传成经过认证的安全急停。

系统恢复要比正常启动更严格：故障清除前旧命令不能自动复活，重新获得控制权后也应从安全状态开始。这个原则能阻止短暂重连把设备带回不可预期运动。

建议把输入条件、输出状态、超时和错误码写入同一接口合同，再用正常、边界与故障三组测试证明。这样更换硬件或算法后，应用仍有稳定判断依据。

# **控制链路**

“控制链路”回答的是一项具体工程问题。PC 命令、ESP32 协调、N32 执行、电机驱动和传感器反馈。设计时既要描述正常路径，也要写出数据过期、设备离线和参数越界时的结果。

双 MCU 分工只有在通信合同清楚时才成立。帧头、长度、命令号、序号、CRC、状态码、超时、重发和版本兼容都要被定义；重复帧还要保证不会重复执行危险动作。ESP32 与 N32 的心跳应互相监督，使任一侧重启都能把执行器带回可预测状态。

状态设计最好采用“值、有效标志、采样时间、来源、故障原因”的组合。这样同一个上位程序既能处理真实硬件，也能处理回放数据或仿真数据，而不会把缺失值误当成真实测量。

验收时应保留原始记录、固件版本、接线方式和测试环境，避免把偶然成功当成能力。能重复、能定位、能恢复，才是从 Demo 走向产品的关键。

# **异常分支**

从产品实现看，“异常分支”不能停留在功能名称上。目标丢失、障碍物、断网、摄像头断开和用户说“停止”时如何处理。每一项都应落到接口字段、运行状态或验收动作，避免应用只能依靠经验猜测。

OV2640 一类摄像头常在板端输出 JPEG，图像大小会随分辨率、质量和画面复杂度变化。传输策略应设置队列上限和过期丢帧，优先保证最新画面；同时把采集、编码、发送和电机 RPC 分开调度，避免图像阻塞控制路径。

课程设计可以让学生先预测系统在异常下的行为，再实际拔线、遮挡传感器或结束进程，最后对照日志解释结果。这样的实验比只完成动作更能建立机器人系统思维。

实现上应优先保证状态语义一致：成功必须有证据，失败必须有原因，数据过期必须可见。上层算法由此可以选择继续、降级、重试或停止。

# **数据复盘**

读者在“数据复盘”中真正需要掌握的是方法，而不只是结论。将语音、计划、视觉、动作和故障放到统一任务时间线。把这些条件写成流程后，开发者才能定位问题属于算法、通信、执行器还是供电。

结构化运动数据至少应包含 timestamp、device_id、task_id、transport、命令、反馈、运行状态和故障原因。CSV 适合快速画曲线，JSONL 适合保留嵌套状态，summary.json 适合验收汇总。三者共享同一任务 ID 后，现场问题才能从结果追溯到过程。

测试证据应覆盖正常路径、边界参数和故障路径。正常路径证明功能可用，边界参数证明校验有效，故障路径证明系统能停止和恢复；三者缺一，能力表都只能标为开发预览。

这类功能适合做成独立实验：先验证单模块，再验证并发，最后注入断线、重启和异常输入。每一步都有 PASS/FAIL，市场宣传才有可追溯依据。

# **结论**

前面的分析可以归并成一个清楚判断：一句话背后是完整的感知-决策-执行闭环。这个判断同时约束产品定义与实现方法。高层可以持续升级算法，底层必须保持接口、状态和失败行为稳定；只有两者都成立，系统才有长期演进空间。

对读者而言，最重要的不是记住一串接口名，而是形成一套判断顺序：先确认任务与风险，再选择架构和硬件，随后验证正常、边界与故障路径，最后才讨论性能与规模。这个顺序能让技术决策和采购决策使用同一组证据。

正式发布时，结论中的每个能力都应对应版本化文档或测试结果。无法提供证据的内容可以作为路线图说明，但不应与当前交付能力混写。

# **PyMotion 的产品判断**

PyMotion 在案例中扮演技能执行与状态反馈节点：它不判断“红色积木是什么”，但负责把转向、接近、停车等动作可靠送到执行器。

真正有价值的控制器，不只是把电平送到接口，而是把动作变成有身份、有边界、有状态、可停止、可复盘的任务。这种能力会直接减少调试时间，也让学校课程、开发者原型和 OEM 评估能够沿同一套接口逐步升级。
